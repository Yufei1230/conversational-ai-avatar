# Audio input and conversation behavior

This document describes the inspected implementation. Paths beginning with `/Game/` refer to assets in the separate local `MetaHumanTest` project.

## Startup introduction

The existing character Blueprint, `/Game/MetaHumans/NewMetaHumanCharacter/BP_NewMetaHumanCharacter`, handles BeginPlay by calling NVIDIA's `AnimateCharacterFromSoundWaveAsync` with the imported `/Game/TestAudio/english-e2e` SoundWave and `LocalA2F-Mark`.

The SoundWave's import metadata identifies `services/orchestrator/outputs/english-e2e.wav`. Its source-file hash matches the inspected WAV. The corresponding saved response report records an earlier real-provider turn:

- Input transcript: ?Hello. Please introduce yourself in English in one short sentence.?
- Generated answer: ?Hello! I'm Kagawa, your conversational virtual assistant. I'm here to help with questions, tasks, or just chat whenever you need.?

The introduction was generated by the LLM/TTS pipeline **when that clip was created**. Each subsequent press of Play reuses the imported clip; it does not run ASR, LLM, or TTS again. It still runs Audio2Face for speech-driven animation. Replacing the original disk WAV alone does not reimport the Unreal SoundWave.

## Which WAV is which?

These local files are under `services/orchestrator/outputs/`, an ignored artifact directory. They are not promised as downloadable samples in a fresh clone.

| File | Actual role | Inspected format |
|---|---|---|
| `demo-input.wav` | Prerecorded **question** asking for an introduction; used by the CLI for a dynamic turn | PCM16, 16 kHz, mono; about 3.58 s |
| `demo-question.wav` | Prerecorded **question** recognized as ?What is the capital of Japan?? | PCM16, 16 kHz, mono; about 1.53 s |
| `english-e2e.wav` | Earlier synthesized **answer**, imported as the startup SoundWave | PCM16, 44.1 kHz, mono; about 7.80 s |
| CLI `--output` WAV | Newly synthesized answer, with a JSON report alongside it | Received TTS rate; 44.1 kHz in the inspected English setup |
| Unreal `Saved/ACEConversation/<GUID>.wav` | Temporary full-response input to ACE | PCM16 mono at the received TTS rate |

`--generate-input` uses hosted TTS to create the fixed introduction **question**, then submits it to ASR ? LLM ? TTS. It writes `demo-input.wav` beside `--output` and can replace an existing file there. Use `--wav` for personal recordings.

## Dynamic question: exact data path

1. `demo_client.py` reads an uncompressed PCM16, 16 kHz, mono WAV. It validates the format without resampling. It splits input into 320-sample / 640-byte / 20 ms frames and zero-pads the final short frame.
2. The CLI creates a session UUID, opens `/ws/session?publish=metahuman-demo`, sends `session.start`, sends ACE1 microphone frames, and ends input with `mic.end`. `--realtime` adds transport pacing; it does not play audio.
3. `ConversationSession` handles VAD or explicit input completion. The current Riva ASR adapter buffers the utterance and calls `offline_recognize`, including when a configured model name contains ?streaming.?
4. The LLM receives the system prompt and current transcript. Its SSE text deltas are assembled into sentences. The TTS consumer synthesizes those sentences in order.
5. Hosted TTS returns a WAV per synthesis request. The adapter extracts PCM and emits approximately 100 ms chunks. JSON events and ACE1 PCM frames go to the publisher and registered observers unchanged.
6. Unreal's `ConversationBridgeComponent` emits TTS start/chunk/end delegates. The MetaHuman receiver buffers the response until `tts.end`, preserves the received sample rate, and writes a temporary PCM16 mono WAV.
7. `AMetaHumanTtsReceiver` calls `AnimateCharacterFromWavFileAsync` on the existing character with `LocalA2F-Mark`. NVIDIA's runtime supplies audio and facial curves to the existing `ACEAudioCurveSource`. The face animation graph consumes those curves.
8. ACE plays the response and advances facial animation against its audio clock. The adapter does not add a second speaker or replace the MetaHuman animation Blueprint.

Network audio is chunked, but the MetaHuman does not speak while those chunks arrive. Audio2Face submission begins after the complete response is buffered. Completed audio submissions remove their temporary input WAV; interrupted sessions can leave runtime files in `Saved`.

## Routing, sessions, and repeat questions

| Question | Current answer |
|---|---|
| Can another question be submitted? | Yes. Keep Unreal running, wait for playback completion, and invoke the CLI again. Earlier real responses and a synthetic two-publisher test cover this pattern. |
| Can one backend WebSocket handle more turns? | The state machine resets to `LISTENING` and can accept another turn. The shipped CLI exits after one turn; a persistent multi-turn client workflow is not demonstrated by the saved tests. |
| Does the LLM remember earlier answers? | No. Its payload contains only `system` and the current `user` message. Logs are not read into later requests. |
| Does reusing `metahuman-demo` preserve context? | No. It only matches publishers to observers. |
| Is a WAV playlist supported? | No native playlist or playback-aware queue. A manually paced sequence of CLI invocations uses existing operations. |
| Does Unreal receive later responses automatically? | Yes, while its observer is connected and not busy. Completed publisher disconnects leave the observer registered. |
| Are failures retried or replayed? | No replay or automatic Unreal reconnect. An incomplete publisher disconnect or observer backpressure can close the observer. Re-enter Play and wait for readiness. |

Only one publisher can own a channel at a time. Observers must register first and cannot submit audio. Routing is in-process, requiring one backend worker. The receiver rejects overlapping responses, invalid/mixed-rate PCM, and buffers exceeding 64 MiB.

## What ?finished? means

| Signal | Meaning | Safe to submit the next question? |
|---|---|---|
| Backend `tts.end` | All TTS chunks sent; Unreal can finalize its WAV | No |
| Backend `state: LISTENING`, `reason: turn_complete`; CLI exits | Backend turn finalized, response available to CLI | No: playback may be pending or active |
| `ACE audio send completed successfully; awaiting playback completion.` | Audio submission to NVIDIA finished | No |
| `Response completed: ACE synchronized audio and animation playback ended.` | Receiver saw both send completion and animation/audio playback end | Yes, after confirming the visible/audible response ended |

There is **no playback-finished acknowledgement from Unreal to the backend**. CLI exit, a fixed delay, or `turn_complete` alone cannot implement a reliable automatic playlist.
